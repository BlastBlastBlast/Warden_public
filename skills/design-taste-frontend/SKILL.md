# tasteskill: Anti-Slop Frontend Skill

> Landing pages, portfolios, and redesigns. Not dashboards, not data tables, not multi-step product UI.
> Every rule below is **contextual**. None of it fires automatically. First read the brief, then pull only what fits.

## 1. Read the brief before you design

Most bad AI design output comes from jumping to a default aesthetic instead of reading the room. Before touching code, work out: the page kind (landing, portfolio, redesign, editorial), the vibe words used, any reference links/screenshots/competitors named, the audience (the audience picks the aesthetic, not your taste), existing brand assets (starting material for redesigns, see Section 6), and quiet constraints (accessibility-first, public-sector, regulated, kids' products) that override aesthetic preference entirely.

State the read in one line before generating anything: *"Reading this as: \<page kind> for \<audience>, with a \<vibe> language, leaning toward \<design system/aesthetic family>."* If the read genuinely diverges between plausible options, ask exactly one clarifying question — never a multi-question dump. If you can confidently infer it, don't ask; declare the read and proceed.

Reach past the model's own defaults deliberately: AI-purple gradients, a centered hero over a dark mesh, three equal feature cards, glassmorphism applied to everything, infinite-loop micro-animation on every element, Inter + slate-900 by default. None of these are wrong in the right brief — they're wrong as the *unexamined* choice.

## 2. Set the three dials

Every layout, motion, and density decision below is gated by three dials, baseline **`DESIGN_VARIANCE: 8` / `MOTION_INTENSITY: 6` / `VISUAL_DENSITY: 4`** (1 = symmetric/static/airy, 10 = chaotic/cinematic/cockpit-dense). The design read moves these — a calm B2B brief pulls variance and motion down; an Awwwards-experimental agency brief pushes them up; a trust-first or public-sector brief pulls density up and everything else down. Overrides happen conversationally; never ask the user to hand-edit dial numbers in a file.

Load `references/dials.md` for the full signal-to-dial inference table, use-case presets, and precise per-level technical definitions — what "motion 4-7" actually means in CSS terms, and the mobile-collapse rule for high-variance layouts.

## 3. Choose the right foundation

If the brief reads as a recognizable design system (Fluent, Material, Carbon, Polaris, Atlaskit, Primer, GOV.UK, USWDS, Radix Themes, shadcn/ui, Bootstrap, Tailwind-based indie SaaS), install and use the *official* package rather than recreating its CSS by hand or importing its tokens and overriding most of them. One system per project — don't mix Fluent with Carbon, or shadcn into a Material 3 app.

If the brief names an aesthetic rather than a system (glassmorphism, bento, brutalism, editorial, dark-tech, mesh gradients, kinetic type, "Apple Liquid Glass"), there's no official package — build it in native CSS/Tailwind and say so honestly in comments. Apple Liquid Glass in particular has no public web CSS equivalent; label any `backdrop-filter` approximation as an approximation, not the real thing.

Full system-to-package mapping, install commands, canonical doc links, and a labeled Liquid-Glass approximation skeleton live in `references/design-systems.md` — load it when picking or wiring up a foundation.

## 4. Core judgment criteria

**Stack & state.** Keep anything using Motion, scroll listeners, or pointer physics in an isolated client component; server components render static layout only. Track continuous, high-frequency input (mouse position, scroll progress, drag) with Motion's `useMotionValue`/`useTransform`/`useScroll`, not `useState` — state re-renders the tree every frame and collapses on mobile. Reuse an icon library instead of hand-rolled SVG paths, one family per project. Prefer CSS Grid over flexbox percentage math, and `min-h-[100dvh]` over `h-screen` for full-height sections. Check `package.json` before importing a third-party library; never assume one exists. Emoji stay out of code, markup, and copy by default — icon glyphs instead, except when the brief explicitly wants a playful/chat-native voice, used sparingly even then. Full stack defaults, breakpoints, and icon-library priority order live in `references/patterns.md`.

**Typography.** Sans is the default display choice, not serif — "creative brief = serif" is the single most-tested AI tell in production rounds, and reaching for it needs a real reason (the brand brief names a serif, or the aesthetic is genuinely editorial/luxury/heritage and you can say why this serif fits this brand). Pick a typeface with a point of view (Geist, Outfit, Cabinet Grotesk, Satoshi, or a justified serif) rather than defaulting to Inter, which earns its place back for a deliberately neutral, Linear-style, or accessibility-first brief. When emphasizing a word inside a headline, use italic or bold of the *same* family; injecting a second font family for emphasis reads as amateur. Italic display type with a descender letter (`y g j p q`) needs `leading-[1.1]` minimum plus a little reserved padding, or the descender clips. `references/ai-tells.md` carries the banned/rotating serif pool and font-pairing suggestions.

**Color.** One accent color, used identically everywhere — once picked, it doesn't drift to a different hue in a later section. Keep saturation restrained and avoid defaulting to the "AI purple/blue glow" aesthetic (neutral bases — zinc/slate/stone — with one high-contrast accent read as designed; purple is fine when the brand actually is purple). Premium-consumer briefs (cookware, wellness, artisan, DTC home goods) have their own well-worn default — warm cream/beige with brass/clay/oxblood accents and espresso text — that most generated sites in that space reach for, erasing the brand. Rotate through a genuinely different palette family (cold-luxury silver/chrome, deep forest + bone, true black + tan, cobalt + cream, terracotta + slate, monochrome + one saturated pop) unless the brand brief explicitly names the cream/brass palette. The exact banned hex families and rotation list live in `references/ai-tells.md`.

**Layout.** Centered hero/H1 sections read as the default the moment `DESIGN_VARIANCE` climbs past ~4 — reach for a split, asymmetric, or scroll-pinned structure instead, unless the brief is a manifesto/launch page where the message itself *is* the design. Use cards only where elevation communicates real hierarchy; otherwise a border or whitespace does the job, and above `VISUAL_DENSITY 7` skip card containers entirely. Tint shadows to the background hue rather than dropping a flat black one. Pick one corner-radius system for the whole page (sharp, ~12-16px soft, or full-pill) — mixing is fine only with a documented rule applied everywhere.

Hero content needs to fit the initial viewport: headline ≤2 lines, subtext ≤20 words and ≤4 lines, CTA visible without scrolling. Size the headline and hero asset together — a large asset with a long headline doesn't also get `text-7xl`. Keep hero top padding modest (`pt-24` or less at desktop) so content doesn't float mid-viewport, and keep the hero itself to at most an eyebrow, a headline, subtext, and CTAs — a trust strip, pricing teaser, or feature bullets belong in the section below, not stacked into the hero. Navigation fits one line at desktop and stays under ~80px tall; condense labels or collapse to a hamburger before letting it wrap.

Repeating the same section layout family (three-column cards, a left-image/right-text split, a full-width quote) gets templated fast — an 8-section page should show at least 4 distinct layout families, and the same image/text split shouldn't run more than twice in a row. Small uppercase "eyebrow" labels above every section headline are the most over-used pattern in production tests — cap them at about one per three sections (hero counts as one), or drop the label. A big headline with a small floating explainer paragraph beside it looks unfinished; stack them vertically unless that column carries a real visual. Size a bento grid to the content you have (3 items → 3 cells, not 3 plus an empty one) and give 2-3 cells real visual weight — an all-white grid of text-only cards reads flat. Every multi-column section needs its own explicit mobile fallback.

**Interactive states & forms.** Ship all four states — loading (skeletal, shaped like the real content, not a generic spinner), empty (composed, with a next action), error (inline for forms, toast only for transient), and tactile feedback on press (`scale-[0.98]` or a 1px lift). Every CTA's text must be readable against its background (WCAG AA, 4.5:1 body / 3:1 large text) — white-on-white buttons and unbounded ghost buttons over photos are the recurring failure. CTA labels fit on one desktop line; if a label wraps, shorten it (aim 1-3 words) rather than constraining the button's width. Two CTAs that mean the same thing ("Get in touch" and "Let's talk" both on the page) should collapse to one label used everywhere. Forms get the same contrast bar applied to inputs, placeholders, focus rings, and helper/error text; labels sit above inputs, never as a placeholder standing in for one.

**Images & content.** These are visual products — check for an image-generation tool first for hero/product/texture assets; fall back to real photography (`picsum.photos/seed/{description}/{w}/{h}` or provided brand assets) only when no gen tool exists; and if neither is available, say so explicitly with labeled placeholder slots rather than filling space with div-based fake screenshots or hand-rolled decorative SVGs. Even a restrained, minimalist brief still wants 2-3 real images — pure text is incomplete work, not minimalism. A "trusted by" logo wall sits below the hero, never inside it, uses real SVG marks (Simple Icons/devicon, or a generated monogram for invented brands) rather than plain-text wordmarks, and shows nothing but the logo.

Keep each section to a short headline (~8 words) and short sub-copy (~25 words) plus one visual or CTA; longer needs a reason. Long lists (>5 items) or spec sheets read better as a grouped, card, tab, or carousel treatment than a bulleted list or a table with a hairline under every row. Before shipping, re-read every visible string for broken grammar, unclear referents, or forced AI-sounding wordplay, and flatten anything that doesn't read like a person wrote it. Numbers should be real, explicitly marked as mock, or dropped — don't invent fake-precise stats (92%, 4.1×) to borrow rigor the brand hasn't earned. Testimonial quotes stay to about 3 lines, attributed by name + role (+ company), never name alone. `references/patterns.md` has the fuller list-pattern and spec-sheet alternatives, plus copy-register and quote-typography detail.

**Theme consistency.** The page commits to one theme — light, dark, or system-auto — and every section honors it; a warm-paper section sandwiched between dark ones reads as a different site mid-scroll (a single deliberate full-page theme-switch moment is the one exception). Design and test both light and dark from the start for any consumer-facing page: keep contrast, hierarchy, and brand-color fidelity equivalent in both, and use off-black/off-white rather than pure `#000`/`#fff` for depth.

For naming these patterns in conversation or code comments, `references/vocabulary.md` lists the standard terms (hero paradigms, nav/menu patterns, scroll effects, micro-interactions). If a project accumulates reusable sections over time, `references/block-library.md` has the file layout and frontmatter schema to keep them consistent.

`references/ai-tells.md` catalogs the broader set of AI-signature patterns worth a final skim before shipping — generic names ("John Doe"), startup-slop brand names ("Acme", "Nexus"), decorative status dots, section-number eyebrows, scroll cues, version labels/footers, hero clutter, locale strips, and more. One item earns calling out on its own: the em dash (—) is the single most over-used AI stylistic tic in production tests — treat it as absent from your vocabulary; a period, comma, or hyphen always does the job instead.

## 5. Motion

Every animation should answer "why does this move?" — hierarchy, storytelling sequence, feedback, or a state transition. "It looked cool" isn't a reason, and reaching for GSAP just because it's available is a tell on its own. Reach for glassmorphism, magnetic hover physics, or perpetual micro-interactions (pulse, shimmer, float) only when `MOTION_INTENSITY` and the brief's vibe both call for them — not every card needs an infinite loop, and a page that claims high motion but ships static is as broken as one that over-animates. One horizontal marquee per page is plenty; a second reads as filler.

Animate only `transform` and `opacity` — never `top`/`left`/`width`/`height`/`margin`. Never drive scroll effects off a raw `window.addEventListener("scroll")` or a `requestAnimationFrame` loop that touches React state; use Motion's `useScroll`, GSAP's ScrollTrigger, or CSS scroll-driven animations instead. A sticky-stack or horizontal-pan effect needs its ScrollTrigger pinned at `start: "top top"` (not `"top center"` or `"top 80%"`) or it fires from the wrong point in the scroll — `references/skeletons.md` has working sticky-stack, horizontal-pan, and lighter Motion `whileInView` skeletons to build from, the fuller list of banned scroll-handling patterns, and when to reach for Motion vs. GSAP vs. Three.js (never mixed in the same tree).

Anything above `MOTION_INTENSITY 3` needs to honor `prefers-reduced-motion` — infinite loops, parallax, scroll-hijacks, and magnetic physics should collapse to static/instant, not just slow down. Keep Core Web Vitals in mind: LCP under 2.5s (priority-load the hero image), INP under 200ms, CLS under 0.1 (reserve space for images/fonts/embeds). Apply grain/noise only to a fixed, `pointer-events-none` layer, keep z-index usage systemic rather than scattered `z-10`/`z-50` values, and lazy-load heavy libraries (Three.js, large motion bundles) that aren't above the fold.

## 6. Redesigns

Detect the mode before touching anything: greenfield (no existing site, or an approved full overhaul), preserve (modernize without breaking the brand), or overhaul (new visual language, same content/IA) — ask once if it's ambiguous. For preserve/overhaul, audit first — brand tokens, IA and conversion paths, what's doing work vs. filler, the site's current dial reading (your starting point, not the baseline), and the SEO baseline (route slugs, meta, structured data — the single biggest redesign risk). Unless asked otherwise, keep IA, nav labels, form field names, and existing accessibility wins intact, and extract the brand's actual colors before applying the color criteria above (a brand that's already purple stays purple). The full preservation checklist is in `references/patterns.md`.

Apply modernization in order of value-to-risk and stop once the brief is satisfied: typography refresh, spacing/rhythm, color recalibration, a motion layer on existing components, hero/key-section recomposition, and only then full block replacement. If IA/content/SEO are sound, targeted evolution (the first four levers) gets most of the value at a fraction of the risk of a full redesign; reach for a full redesign only when the visual debt is structural (broken IA, no design system, broken mobile), and for a full brand change, treat it as greenfield.

## 7. Out of scope

Not for dashboards, dense product UI, or admin panels (reach for Fluent/Carbon/Atlaskit/Polaris instead); not for data tables (TanStack Table/AG Grid); not for multi-step forms/wizards; not for code editors (Monaco/CodeMirror); not for native mobile (HIG/Material directly); not for realtime collab UI (presence/cursors — a different problem class). If the brief is one of these, say so and point to the right tool rather than forcing this skill's patterns onto it.

## 8. Pre-ship checklist

Before calling the page done: the design read and dial values are stated, not silently defaulted; one design system is in use throughout; the accent color, corner-radius system, and light/dark theme are consistent across every section; every CTA and form field passes contrast and no CTA wraps; the hero fits the viewport with the right stack of elements; images are real (or explicitly flagged as missing) rather than fake screenshots; copy has been re-read for AI tells and broken grammar; motion is justified, GPU-safe, and reduced-motion-safe; and nothing on the page uses an em dash. This is a sample of the highest-impact checks, not the full list — the criteria above and `references/ai-tells.md` cover the rest; if something there would fail, the page isn't done.
